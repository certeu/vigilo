## Step 2: Run the Six-Question Checklist on Every Finding

For every finding in `findings_index.json`, work through these six questions in order. Each question can produce a downgrade, a framing correction, or a `conditional_on` flag.

### Q1 — Does the citation actually match?

The finding cites a file and (usually) a line number. Open it. Read the code at that line.

- Does the cited line contain what the finding claims?
- If the finding cites a config key (e.g. `main.ini:525 → portal.internal_token`), grep for the key — is that line really that key, or a different one?
- If the finding cites a vulnerable function call, is the function call really there, or did the specialist misread surrounding code?

If the citation is wrong, set `confidence = "theoretical"` and write the discrepancy in `framing_correction`. Do NOT preserve the original severity — downgrade to at most `low` unless you can find the same vulnerability at a different location yourself.

### Q2 — Are the preconditions complete?

Read the cited code path back to its entry point. What does the attacker actually need to reach this sink?

- Does the path require authentication? (Look for decorators, middleware, `request.authenticated_userid` checks.)
- Does it require admin or a specific role?
- Does it require a particular HTTP method, header, or content type?
- Does it require the user to be in the same tenant / organisation / constituent?
- Does it require an admin to have configured something out-of-band (e.g. subscribed to an iCal feed, federated an external IdP)?

If the finding is framed as "unauthenticated" but actually requires a valid token, that is a **framing correction**, not just a precondition note. Record:
- `framing_correction`: short prose explaining the corrected framing
- `preconditions`: array of strings, each one a concrete thing the attacker needs

If the corrected framing reduces blast radius substantially (unauthenticated → authenticated, any-user → admin-only, any-tenant → same-tenant), downgrade severity by one step.

### Q3 — Does severity match feasibility?

A finding can be real and still mis-graded. Critically check:

- **Brute-force / oracle vulns:** is the keyspace small enough and rate limiting absent enough to actually be exploitable in human time? If status says "Exploited" but the math says "would take days at infinite QPS" — that is "Potential", not "Exploited". Write the math in `rationale`.
- **Race conditions:** is the window realistic, or microseconds-narrow on a single host?
- **Cryptographic weaknesses:** does the weak primitive actually leak something useful, or is it defended-in-depth by other layers (e.g. UUID4 hashed with SHA-224 — UUID4 already has 122 bits of entropy, the hash is irrelevant)?
- **Timing attacks:** is the timing difference large enough to be measured remotely with realistic noise (not just "non-constant-time on paper")?

If severity does not match feasibility, set `severity_adjusted` and explain in `rationale`. The status bucket may also need to move from "Exploited" to "Potential".

### Q4 — Is the finding gated by a config flag, feature toggle, or build option?

Many findings only fire if a deployment opts in. Common gates:

- INI / YAML config: `ldap.sync_user_data = False`, `cors.allow_all = False`, `debug = False`.
- Environment variables: `DEBUG`, `ENABLE_X`, `FEATURE_Y`.
- Code-level booleans: a `if FEATURE_FLAG_X:` guard around the vulnerable path.
- External preconditions: "only exploitable if Keycloak federates with untrusted external IdPs", "only if an admin subscribes to an attacker-controlled iCal feed".

For each finding, search the repository for flags that gate the vulnerable code path:
```bash
grep -rn "ldap\|sync\|federat\|enable_\|feature_" --include="*.ini" --include="*.yaml" --include="*.py" | head -50
```

If a gate exists and is **off by default**, mark `conditional_on` with the exact flag and value (e.g. `"ldap.sync_user_data=True"`, `"keycloak federates with untrusted external IdP"`). Severity stays the same numerically but the *practical* severity is reduced by the precondition — the report and remediation agents render this explicitly.

### Q5 — Does the finding's own text contradict its rating?

Specialists sometimes write hedging language and then ship a high severity anyway. Look for self-contradicting phrases in the evidence:

- "Unconfirmed... no current usage was found" + High severity → demote to Informational.
- "The practical impact is minimal" + Medium severity → demote to Low.
- "Theoretical only" / "Hypothetical" / "If a developer were to..." → defense-in-depth or theoretical.
- "Requires social engineering of an admin" + Critical → almost always demote one step (chain involvement is realistic, but on its own, social engineering preconditions cap severity at High).

If the evidence text contradicts the severity, downgrade and quote the contradicting phrase in `rationale`.

### Q6 — Is this defense-in-depth or a real vulnerability?

A real vulnerability has a demonstrable impact path (data leak, auth bypass, code execution, privilege escalation). Defense-in-depth findings are *good practice violations* whose absence does not directly create exploitable impact:

- `==` instead of `compare_digest` on a value that is not actually a secret being timing-leaked across the network.
- Weak hash on a value with sufficient entropy from a stronger upstream source.
- Missing CSP headers on a path that has no XSS sink.
- Bcrypt non-constant-time on the verify path (bcrypt is itself slow enough that practical timing leakage is negligible).

If the finding is defense-in-depth:
- `confidence = "defense-in-depth"`
- `severity_adjusted` to `low` or `informational` regardless of the original
- The report agent will demote these to an appendix and the remediation agent will skip them.

## Step 3: Build the Annotation Map

For every finding in `findings_index.json`, emit an annotation object. **The keys in `annotations` MUST match the canonical IDs in `findings_index.json` exactly** (same VULN-IDs, same CHAIN-IDs).

Annotation schema (every field is required; use `null` or `[]` when not applicable, not omission):

```json
{
  "confidence": "confirmed | potential | conditional | theoretical | defense-in-depth",
  "severity_original": "critical | high | medium | low | informational",
  "severity_adjusted": "critical | high | medium | low | informational",
  "reachability": "external | authenticated | admin_only | internal_only | mitigated_by_deployment",
  "group_id": "sqli-user-search",
  "include_in_report": true,
  "possible_false_positive": false,
  "preconditions": ["valid JWT", "user in same tenant"],
  "conditional_on": "ldap.sync_user_data=True",
  "framing_correction": "Was framed as unauthenticated; actually requires a valid JWT and only leaks the requesting user's own up_api_token.",
  "rationale": "Citation matches; preconditions added (auth required); severity unchanged.",
  "evidence_supports_status": true,
  "status_adjusted": "Exploited | Potential | Unconfirmed (Analysis) | Unconfirmed"
}
```

Field semantics:

- `confidence` — your verdict on the finding's grounding. Definitions:
  - `confirmed` — citation matches, preconditions are realistic, severity matches feasibility, evidence demonstrates the impact. Ship as-is.
  - `potential` — real vulnerability, but exploitation has not been demonstrated end-to-end (e.g. "Exploited" was overclaimed; actually only "Potential").
  - `conditional` — real vulnerability, but only fires when a feature flag / config gate / external precondition is true. The `conditional_on` field MUST be populated.
  - `theoretical` — citation is wrong, evidence does not support the claim, OR the attack model requires preconditions that make it implausible in this deployment.
  - `defense-in-depth` — code-style / hardening issue with no demonstrable exploitable impact in this codebase. Should not be patched as a vuln; should appear in the report appendix only.

- `severity_original` — copy verbatim from `findings_index.json`. This preserves audit trail.
- `severity_adjusted` — your corrected severity. May equal the original if no adjustment is warranted. Defense-in-depth maps to `low` or `informational`. Theoretical maps to at most `low` unless you re-discovered the same vuln elsewhere.
- `reachability` — who can actually reach the vulnerable path in THIS deployment, judged against the deployment facts in `shared_context.json` (auth model, network exposure, admin-only surfaces, tenant isolation) and the code's own guards. One of: `external` (anonymous internet), `authenticated` (any logged-in user), `admin_only` (requires an admin/privileged role), `internal_only` (only reachable from an internal network / behind a proxy the public cannot hit), `mitigated_by_deployment` (a deployment control — reverse proxy allowlist, network policy, WAF rule confirmed in config — neutralises it). This is the operator's #1 false-positive source: a "critical SQLi" that only an admin behind an internal proxy can reach is not critical. `internal_only` and `mitigated_by_deployment` almost always drop `severity_adjusted` and usually mean `include_in_report=false` (record it, don't headline it).
- `group_id` — a short stable slug naming the ONE underlying issue this finding is an instance of. Findings that are the same root vulnerability surfaced at different locations, flows, or variants MUST share a `group_id` (this is how duplicates are collapsed — there is no separate dedup step; you are it). Distinct issues get distinct slugs. Example: three reflected-XSS findings in the same unescaped render helper all get `group_id: "xss-render-helper"`.
- `include_in_report` — `false` to keep the finding out of the main report body (it is still recorded in this file for audit, never silently dropped). Set `false` for `theoretical`, `defense-in-depth`, `reachability in {internal_only, mitigated_by_deployment}`, and any finding you judge not a real, in-context vulnerability. Set `true` for genuine, reachable findings — including `conditional` ones (they are real, just gated). Quality over quantity: a report of 6 solid findings beats 40 noisy ones.
  **Recall floor (hard rule):** you may NOT set `include_in_report = false` for a finding whose `severity_adjusted` is `critical` or `high` AND whose `reachability` is `external` or `authenticated`. A serious, reachable bug always reaches the report body. If you believe such a finding is not real, the correct move is to lower `severity_adjusted`/`reachability` with an evidenced `rationale` (which then legitimately changes inclusion) — never to hide a still-critical, still-reachable finding. If you are unsure, keep it in and set `possible_false_positive = true`.
- `possible_false_positive` — `true` when the finding is plausibly real but you could not fully confirm it and a reader should treat it with caution (surfaced in the report as an explicit caveat rather than asserted as fact). Use this instead of silently dropping a finding you are merely unsure about.
- `preconditions` — explicit list. Include auth requirements, role requirements, network position, prior knowledge the attacker needs. If genuinely none, use `[]`.
- `conditional_on` — single string description of the gate that must be true for exploitation. `null` when not gated. Required when `confidence == "conditional"`.
- `framing_correction` — short prose (≤2 sentences) describing how the finding was misframed. `null` if framing is correct.
- `rationale` — short prose (≤3 sentences) summarising what the six-question pass concluded. Always populated.
- `evidence_supports_status` — `true` if the original `status` field in the finding (Exploited / Potential / etc.) is supported by the evidence file, `false` otherwise.
- `status_adjusted` — your corrected status bucket. Use the four legend values verbatim: `Exploited`, `Potential`, `Unconfirmed (Analysis)`, `Unconfirmed`. Equal to the original when unchanged.

## Step 6: Self-Validation

Before exiting, re-read the saved critique and check:

1. Every canonical ID in `findings_index.json` has exactly one entry in `annotations`. No extras, no omissions.
2. Every annotation has all required fields populated (no missing keys, no missing values where the schema requires a value).
3. Every `confidence == "conditional"` entry has a non-null `conditional_on`.
4. Every `confidence == "defense-in-depth"` entry has `severity_adjusted` of `low` or `informational`.
5. Every `framing_correction` field is either `null` or a non-empty string. No empty-string sentinels.
6. The `summary.confidence_counts` totals add up to `summary.total_findings`.
7. The `summary.conditional_findings`, `defense_in_depth_findings`, and `theoretical_findings` arrays are consistent with the per-finding `confidence` values.
8. Every annotation has a `reachability`, a `group_id`, `include_in_report` (bool), and `possible_false_positive` (bool).
9. Every `theoretical` / `defense-in-depth` entry, and every entry with `reachability` in {`internal_only`, `mitigated_by_deployment`}, has `include_in_report = false`.
10. `group_id`s are reused across genuine duplicates (do not give every finding a unique slug — that defeats dedup) and are distinct across genuinely different issues.
11. **Recall floor:** NO annotation has `include_in_report == false` while `severity_adjusted` in {`critical`, `high`} AND `reachability` in {`external`, `authenticated`}. If one does, either it is genuinely serious+reachable (set `include_in_report = true`) or its severity/reachability was wrong (lower it with rationale). A serious, reachable bug must never be hidden.
12. Every `status == "suppressed"` finding from `findings_index.json` has been independently re-examined — not just accepted — and either confirmed suppressed with a rationale or re-promoted.

If any check fails, fix and re-save.

## Constraints

**DO NOT:**
- Invent new findings. The critique annotates the existing inventory; it does not extend it.
- Modify `findings_index.json`, evidence files, or any other deliverable. Your output is `findings_critique.json` only.
- Upgrade severity unless you can cite specific evidence the original specialist missed. Default direction is downward — overclaiming is the failure mode you are correcting.
- Rewrite exploitation steps. Critique is about *grading*, not re-doing the work.
- Skip findings because they look correct. Every finding gets an annotation. "Confirmed" is a valid verdict and most findings should land there if the specialists did good work.

**DO:**
- Be skeptical and explicit. A short rationale citing the file:line you re-read is worth more than a confident verdict with no anchor.
- Treat configuration defaults as authoritative. If `ldap.sync_user_data = False` ships in `main.ini`, then LDAP-injection findings are conditional regardless of how the specialist phrased them.
- Quote the specialist's own hedging language back at them when downgrading. "Specialist wrote: 'no current usage found' — demoted from High to Informational" is a defensible call.
- Use the four legend statuses verbatim in `status_adjusted`: `Exploited`, `Potential`, `Unconfirmed (Analysis)`, `Unconfirmed`.
- Keep the JSON parseable. The downstream agents read it programmatically; a malformed file blocks remediation and the report.

When the critique is complete and self-validation has passed, output: CRITIQUE COMPLETE
