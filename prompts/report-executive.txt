## Step 1: Read ALL Input Files

Read every file in `deliverables/` that is relevant. The pipeline produces these:

**Authoritative source of truth (read this FIRST):**
- `deliverables/findings_critique.json` — the adjudicated finding set. For every finding it records `confidence` (confirmed / potential / conditional / theoretical / defense-in-depth), `severity_adjusted`, `status_adjusted`, `reachability`, `group_id`, `include_in_report`, `possible_false_positive`, `preconditions`, `conditional_on`, `framing_correction`, and `rationale`. **This is the single source of truth for which findings exist, their severity/status, how they group, and what reaches the client.** There is no separate pre-computed stats file — you derive counts, grouping, and inclusion from this file directly. **Apply it silently:** render adjusted severity/status as *the* severity/status, surface preconditions/conditional gates as natural framing, fold framing corrections into the narrative. Never expose this file or a "critique" step to the reader — no "original vs adjusted" labels, no "reviewer note", no rationale dumps. If a specialist's finding was corrected, the corrected version *is* the finding.

**Exploitation evidence** (one per vulnerability category — primary narrative source):
- `deliverables/injection_exploitation_evidence.md`
- `deliverables/xss_exploitation_evidence.md`
- `deliverables/auth_exploitation_evidence.md`
- `deliverables/ssrf_exploitation_evidence.md`
- `deliverables/authz_exploitation_evidence.md`
- `deliverables/graphql_exploitation_evidence.md`
- `deliverables/websocket_exploitation_evidence.md`
- `deliverables/chain_exploitation_evidence.md`

**Analysis deliverables** (provide context, architecture, and analysis-only findings):
- `deliverables/code_analysis_deliverable.md` — tech stack, architecture, code-level findings
- `deliverables/recon_deliverable.md` — attack surface, reconnaissance findings
- `deliverables/crypto_analysis_deliverable.md` — cryptographic findings (analysis only, no exploitation)
- `deliverables/injection_analysis_deliverable.md`, `xss_analysis_deliverable.md`, etc. — per-category code analysis

**Supply chain (SCA)**:
- `deliverables/sca_findings.json` — Software Composition Analysis results: vulnerable third-party packages found in dependency manifests (package.json, requirements.txt, pom.xml, etc.) via the OSV.dev database. Contains `manifests_scanned`, `packages_scanned`, and a `vulnerabilities` list with per-package CVE/advisory details.

**Code integrity**:
- `deliverables/integrity_analysis.json` — Code integrity analysis results: detection of malicious code modifications including backdoors, data exfiltration, obfuscated payloads, credential harvesting, and supply chain tampering. Contains `files_scanned`, `issues_found`, and a `findings` list with per-finding severity, confidence, category, evidence, and whether there is a legitimate explanation.

**Structured data**:
- `deliverables/findings_index.json` — unified vulnerability index. Use it to pull each finding's **body** (fields, source→sink, location) keyed by ID. **Do not derive the inventory or counts from this file** — it is pre-critique and includes suppressed/duplicate entries. The inventory, counts, grouping, and inclusion come from `findings_critique.json`.
- `deliverables/shared_context.json` — tech stack, auth mechanisms, API info discovered during the assessment.

**Remediation**:
- `deliverables/remediation_report.md` — fix branches, files changed, patch descriptions per branch.

**Screenshots**:
- `deliverables/screenshots/` — PNG/JPG screenshots captured during exploitation (check what exists with `ls deliverables/screenshots/`).

Not all files will exist — some categories may have no findings. Read what is available and skip missing files without error.

## Step 2: Build Your Inventory From `findings_critique.json`

The critique is your spine. Build the report's inventory from it — quality over quantity. The reader sees one set of severities, one set of statuses, one framing per finding, and no duplicates.

1. **Group into canonical findings by `group_id`.** Collapse every annotation that shares a `group_id` into ONE canonical finding (the same underlying issue surfaced at multiple locations/flows/variants). Pick the most severe / best-evidenced member as the canonical; list the others' IDs as aliases. Annotations with a unique `group_id` are their own canonical finding. This is the deduplication — there is no pre-deduped list to lean on.

2. **Decide what reaches the report body via `include_in_report`.** A canonical finding appears in the main per-category sections ONLY if at least one of its members has `include_in_report == true`. Findings where every member is `include_in_report == false` (theoretical, defense-in-depth, or `reachability` in {`internal_only`, `mitigated_by_deployment`}) go to the **Hardening Appendix**, not the body. Do not pad the report with these — that is exactly the noise we are cutting. Every annotated finding still appears *somewhere* (body or appendix); nothing is silently dropped.

   **Recovery check (do not skip):** if `deliverables/findings_critique_audit.json` exists and its `missing_annotations` list is non-empty, those finding IDs are present in `findings_index.json` but were not annotated by the critique. Include each one in the report anyway — pull its body from `findings_index.json`, use a conservative severity, and flag it `possible_false_positive`-style ("not fully reviewed; validate before acting"). A missing annotation must never mean a dropped finding.

3. **Apply severity/status/framing silently.** For the canonical finding, use `severity_adjusted` as *the* severity and `status_adjusted` as *the* status. Fold `preconditions`, `conditional_on`, and `framing_correction` into natural prose (not second-opinion callouts). `confidence` drives placement: `confirmed`/`potential`/`conditional` → body (conditional gets a `**Preconditions:** {conditional_on}` line); `theoretical`/`defense-in-depth` → Hardening Appendix. Never print `rationale`.

4. **Flag possible false positives.** For any canonical finding with `possible_false_positive == true`, add a plain-language caveat in its description — e.g. *"This finding could not be fully confirmed in the available context and should be validated before remediation."* Do NOT assert it as proven. This is how the report is honest about uncertainty instead of either dropping the finding or overstating it.

5. **Surface reachability as framing.** Use `reachability` to set the reader's expectation of who can exploit each finding (external / authenticated / admin-only). This is the assumption under which the severity holds — state it in the finding's framing.

6. **Derive counts yourself from the included inventory.** There is no stats file. Count the canonical findings that reach the body, broken down by `severity_adjusted` and by category, and by `status_adjusted`. Use these self-derived counts consistently everywhere a number appears (overview tables, TOC, executive summary). The counts describe the report body (hardening-appendix items are counted separately, in the appendix intro).

7. **Aliases.** When a canonical finding absorbs grouped members, render them in the per-finding heading: `*(Also tracked as: ID-1, ID-2)*`. Preserves the audit trail.

8. **Fix branches — three states, not two.** Read `deliverables/remediation_manifest.json` (structured: `branch`, `finding_ids`, `files_changed`, `pushed`, `diff_nonempty`, `verified`, `verify_method`) to wire each finding to its fix, and classify each into exactly one state:
   - **Delivered** — `pushed == true` AND `diff_nonempty == true`. The fix branch (and MR, if any) is live upstream.
   - **Patch available (local)** — `diff_nonempty == true` AND `pushed == false`. A real, non-empty patch was generated and exported to `deliverables/patches/{ID}.patch`, but not pushed (e.g. code-only run, no upstream/token). This is NOT "unpatched" — the operator can apply the patch; say so.
   - **Unpatched** — no branch, or `diff_nonempty == false` (empty/no-op branch).
   Also read `verified`: `pass` means the fix was **verified** (its confirmation harness no longer reproduces the vulnerability on the patched code); `fail` means the patch did NOT resolve it (flag prominently); `not_tested` means it could not be auto-verified. Never write "verified" unless `verified == "pass"`. If the manifest is absent, fall back to `deliverables/remediation_report.md` prose.

9. **Pull narrative content from the evidence/analysis files** for each canonical finding — exploitation steps, payloads, proof of impact, code locations — keyed by the canonical ID and its aliases. When a `framing_correction` exists, rewrite the description so the corrected framing is the only one the reader sees. Preserve payloads/commands/code citations verbatim; only the summary/severity framing is rewritten.

10. **Screenshots.** Run `ls deliverables/screenshots/` and match files to canonical findings (or their aliases) by VULN-ID in the filename.

## Step 3: Plan and Draft Systemic Root Causes

Before writing per-category sections, look across all canonical findings and identify systemic root causes — single missing defences or shared design flaws that explain multiple findings. Examples of patterns to look for:

- A defence that exists nowhere in the codebase (rate limiting, CSRF tokens, HTML sanitization, SSRF guards, constant-time comparison)
- A guard that is consistently absent on a class of endpoints (e.g. ownership filter on all tenant data reads)
- A configuration omission with broad blast radius (SameSite cookie attribute, TLS verification, secret in repo)
- A shared library or utility that is the choke point (e.g. a rendering helper that emits unsanitised HTML)

For each root cause:
- **Title** — name the missing defence, not a vulnerability category.
- **Description** — explain what is missing and where. Cite specific files or modules.
- **Affected canonical findings** — list at least 2 canonical IDs. Single-finding "systemic" issues are oxymorons; do not include them.
- **Remediation summary** — one paragraph: what library / pattern / configuration to introduce, where to apply it, what to enforce in CI.

Aim for 3–7 root causes. They are not exhaustive — they highlight the *highest-leverage* fixes. A canonical finding can appear in more than one cluster if it genuinely has more than one missing defence.

#### 3. Executive Summary (3-4 paragraphs)

**Paragraph 1 — Scope & Approach:** What was tested, how (automated + manual techniques), assessment context.

**Paragraph 2 — Key Findings:** Most critical discoveries, emphasizing business impact. Lead with highest-severity. If attack chains exist, highlight them as the most realistic threat scenarios.

**Paragraph 3 — Risk Assessment:** Overall security posture. State the unique-finding total and severity breakdown using the counts you derived in Step 2. Lead readers to the highest-leverage fixes: do NOT bury confirmed-critical findings under code-style nits.

**Paragraph 4 — Recommendations:** Top 3-5 prioritized recommendations, drawn from the Systemic Root Causes section. Each recommendation should map to one root cause and address multiple findings at once.

#### 9. Supply Chain (SCA) Section

Render only when there is at least one supply_chain finding. This section lists vulnerable third-party dependencies discovered by Software Composition Analysis. Unlike code-level findings, these are known CVEs in upstream packages — the remediation is upgrading or replacing the dependency.

**Use the DEDUPED set from `deliverables/findings_index.json` → `by_type.supply_chain`** — NOT the raw `deliverables/sca_findings.json`. The index entries have been deduplicated by `(package, advisory)` and annotated with `absorbed_count` (how many raw entries collapsed into this one) and `dependency_used` (`true` = the package is positively imported/used in the code; `unknown` = usage could not be confirmed). `sca_findings.json` may still be read for extra per-CVE detail (summary, version range, fixed version) keyed by advisory.

Lead with `dependency_used == "true"` findings — those are the ones confirmed to be reachable in this codebase — and clearly separate the `unknown`-usage ones (present as a dependency but not confirmed imported) so the reader can triage. State the deduped count, and mention when duplicates were collapsed.

```markdown
## Supply Chain (SCA) Vulnerabilities

Software Composition Analysis identified {N deduped} vulnerable third-party dependencies (from {raw} raw advisories). {K} are in packages confirmed used in the codebase.

### Confirmed-used dependencies
| # | ID | Package | Installed Version | Advisory | Severity | Fixed Version |
|---|-----|---------|-------------------|----------|----------|---------------|
| 1 | SCA-VULN-01 | lodash | 4.17.15 | CVE-2021-23337 | High | 4.17.21 |

### Present but usage unconfirmed
{same columns; dependency_used == "unknown"}

{For each finding, include: the advisory summary, affected version range, and whether a patched version is available.}
```

Supply chain findings are not code-fixable by the remediation agent — they require dependency upgrades. They should NOT appear in the Unpatched Vulnerabilities table (which tracks code-level fixes). Instead, the section itself serves as the actionable remediation guide: upgrade to the fixed version listed, or replace the dependency if no fix is available.

## Step 5: Self-Validation Pass
