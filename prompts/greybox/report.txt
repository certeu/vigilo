## Report Generation Process

### Step 1: Full Graph Export
Export the complete knowledge graph to understand the full assessment:

```bash
graph-tool export --format yaml --max-tokens 15000
```

This gives you:
- All discovered endpoints, parameters, technologies, and workflows
- All test attempts (what was tested and results)
- All confirmed findings with PoC details
- All leads (investigated and open)
- All chain relationships
- Validation results
- Access matrix across identities
- Coverage statistics

### Step 2: Root-Cause Clustering and Inventory

The graph may contain many findings that are technically distinct (different endpoints or parameters) but share the same root cause. For example, "Missing Content-Security-Policy" on 5 endpoints is ONE issue — the application lacks CSP middleware — not five separate vulnerabilities. Similarly, "IDOR via predictable table-name parameter" on 3 query endpoints is ONE authorization gap, not three.

Your job is to cluster findings by root cause so the report reads as a concise list of issues to fix, not a noisy dump of raw graph records.

#### Clustering rules (apply in order)

1. **Exact dedup**: Findings with the same `(vuln_type, target)` are always one finding (the graph already enforces this, but verify).

2. **Root-cause clustering**: After exact dedup, group the remaining findings into root-cause clusters. Two findings belong to the same cluster when they share ALL of:
   - Same `vuln_type` (e.g., both "injection", both "authorization")
   - Same CWE (if present) OR same class of weakness (e.g., both missing a specific header, both exploitable via the same parameter pattern)
   - Same fix — a single code/config change would remediate every instance in the cluster (e.g., "add CSP header middleware", "enforce server-side ownership check on the table-name parameter")

   When in doubt, ask: "Would a developer fix all of these in one pull request?" If yes, they are one root-cause cluster.

3. **Representative selection**: For each cluster, pick the instance with the highest severity, richest PoC evidence, and validation (if any) as the lead finding. Merge supporting evidence and payloads from the others.

4. **Affected-targets list**: Under each cluster's detailed section, list every affected endpoint/parameter as a table — do NOT create a separate detailed finding per instance.

#### Build the report inventory

From the clustered findings:

1. **Root-cause inventory**: List each cluster (one row per root cause), sort by severity, count affected targets per cluster
2. **Chain findings**: Findings with `chains_with` relationships (chains may span clusters)
3. **Validation status**: Check `validated` and `validation_verdict` fields on each finding
4. **Open leads**: Leads with status `open` (mention as areas for future testing)
5. **Coverage metrics**: Calculate tested vs untested across each vulnerability type
6. **Access matrix**: Summarize identity access patterns

### Step 3: Write the Report

Write the report to `deliverables/greybox_assessment_report.md` in chunks (mandatory — do not write entire report in one call).

#### Section 8: Detection Engineering Appendix

For every confirmed finding the specialists populated a `detection_hints`
object on the graph node. This appendix consolidates those hints so the
defensive team can copy-paste directly into their WAF, SIEM, or log
pipeline without re-reading the finding sections. Group by detection
surface (WAF, SIEM, log, network) rather than by finding so SecOps can
run a single pass per surface.

| RC ID | Vuln Type | Why no signal? | Recommendation |

**Generation rules for this section:**

1. **Read every confirmed finding's `detection_hints`** field from the graph
   export. If `detection_hints` is null/missing, the finding belongs in the
   "Coverage Gaps" subsection, not the main tables.
2. **Group by detection surface, not by finding.** A SOC engineer wants
   one consolidated WAF list, one consolidated SIEM query list — not to
   chase the same data scattered across N finding sections.
3. **Cross-reference the RC ID from Section 4** so the reader can jump
   from a WAF rule back to the finding that motivated it.
4. **Do not invent rules.** If a finding's `detection_hints` lacks a
   `waf_rule` key, omit it from the WAF table — do not generate one.
   The specialists are the source of truth here.
5. **Suggest a bundled artefact** at `deliverables/detection/waf_rules.conf`
   when ≥3 WAF rules exist. The reader can ship the file directly to ops
   without rebuilding it manually.

### Report Quality Rules

**DO:**
- Cluster findings by root cause — if one fix resolves multiple findings, they are ONE issue
- Present each root-cause cluster as a single detailed section with an affected-targets table
- Pick the best PoC from each cluster (richest evidence, highest severity, validated)
- Include ALL root-cause issues from the graph with complete PoC details
- Use exact payloads and evidence from graph data — never fabricate
- Sort findings by severity (Critical first)
- Include validation status for each finding
- Calculate and present coverage metrics accurately
- Write one recommendation per root cause that addresses all affected targets
- Reference screenshots where available
- State the consolidation ratio in the executive summary ("N raw findings → M root-cause issues")
- Render every confirmed finding's `detection_hints` field in the Detection Engineering Appendix (Section 8) — consolidated by surface (WAF / SIEM / log / network), cross-referenced by RC ID

**DO NOT:**
- List the same root cause multiple times because it affects multiple endpoints
- Create a separate detailed-findings section for each endpoint hit by the same issue
- Write per-endpoint recommendations when a single architectural fix covers them all
- Invent vulnerabilities, payloads, or evidence not in the graph
- Omit findings because you think they are unimportant
- Use agent-speak ("My mission is complete", "I was tasked with")
- Add severity ratings not supported by the actual demonstrated impact
- Skip the coverage metrics section
