## Authorization Testing Methodology (Grey-Box, OWASP)

### Phase 1: Access Matrix Review
Before testing, review the access matrix from the discovery agent and
any previously-emitted ``can_access`` / ``denied_access`` edges:
1. Query the graph for access records across all identities in scope.
2. Identify endpoints where access differs between roles.
3. Note endpoints with object-ID parameters (IDOR candidates).
4. Flag admin-only endpoints to retest from lower-privilege identities.

```bash
graph-tool claim --id "endpoint:GET_api_users_id" --agent "authorization-specialist" --ttl 600

# Query existing access matrix
graph-tool query --type endpoint --filter "auth_required=true" --limit 50
```

### Phase 2: Horizontal Privilege Escalation (IDOR) — full_matrix only
Test if users can reach other users' resources by manipulating object IDs.

**For each endpoint with an object-ID parameter:**
1. As identity A, access their own resource (e.g. GET /api/users/123).
2. As identity A, attempt to access identity B's resource
   (e.g. GET /api/users/456).
3. Compare responses: if A gets B's data, IDOR confirmed.

```bash
graph-tool test-attempt \
  --target "endpoint:GET_api_users_id" \
  --vuln-type authorization \
  --technique "horizontal-escalation: object-id-swap" \
  --payload "Authenticated as user (id=123), requested /api/users/456" \
  --verdict conclusive_vulnerable \
  --response-code 200 \
  --response-excerpt "Received user 456's profile data including email and phone"
```

**IDOR Enumeration Patterns:**
- Sequential IDs: try id-1, id+1, id+2.
- UUID-based: collect other users' UUIDs from public profiles, API
  responses, or error messages.
- Predictable patterns: username-based, email-based, timestamp-based.
- Parameter pollution: add duplicate parameters
  ``/api/users/123?user_id=456``.

### Phase 3: Vertical Privilege Escalation — vertical_only and full_matrix
Test if lower-privilege identities can reach higher-privilege features.

**Direct Endpoint Access:**
1. Identify admin-only endpoints from the access matrix.
2. Authenticate as a regular identity.
3. Directly request admin endpoints.

```bash
graph-tool test-attempt \
  --target "endpoint:GET_api_admin_users" \
  --vuln-type authorization \
  --technique "vertical-escalation: direct-access" \
  --payload "Authenticated as 'user' role, requested /api/admin/users" \
  --verdict conclusive_clean \
  --response-code 403 \
  --response-excerpt "Forbidden — insufficient permissions"
```

**Method-Based Bypass:**
- If GET returns 403, try POST, PUT, PATCH, DELETE, OPTIONS.
- Try HTTP method override headers:
  ``X-HTTP-Method-Override: GET``.
- Some frameworks honour ``_method=GET`` parameter.

**Header-Based Bypass:**
- ``X-Original-URL: /api/admin/users``
- ``X-Rewrite-URL: /api/admin/users``
- ``X-Forwarded-For: 127.0.0.1`` (IP-allowlist bypass)

**Path Traversal Bypass:**
- ``/api/admin/../admin/users``
- ``/api/admin/users;``
- ``/api/admin/users%00``
- ``/API/ADMIN/USERS`` (case sensitivity)
- ``/api/admin/./users``

### Phase 4: Role Manipulation and Session Integrity
Test if role / privilege information can be modified client-side or
replayed across sessions:
1. Capture a role-defining token or parameter (JWT claim, cookie value,
   hidden form field).
2. Modify the role value (e.g. ``role: user`` → ``role: admin``).
3. Submit the modified request; check whether elevated access is granted.
4. Test session fixation: can a pre-authentication session cookie be
   promoted by logging in without rotation?

```bash
graph-tool finding \
  --target "endpoint:PUT_api_profile" \
  --vuln-type authorization \
  --severity critical \
  --cwe CWE-269 \
  --title "Mass assignment allows role escalation via profile update" \
  --poc-payload "PUT /api/profile with body {\"name\":\"test\",\"role\":\"admin\"}" \
  --impact "Any user can escalate to admin by including role field in profile update" \
  --grants '["admin_access","user_management"]' \
  --requires '["authenticated"]' \
  --evidence-file "deliverables/screenshots/authz-role-escalation.png" \
  --derived-from "test_attempt:ta_XXXX"
```

### Phase 5: Multi-Tenant Isolation — full_matrix only
If the application supports multiple organizations or tenants:
1. Authenticate as a user in tenant A.
2. Attempt to access resources owned by tenant B.
3. Test tenant-ID manipulation in API requests.
4. Check whether data from other tenants leaks through shared endpoints.

### Phase 6: Workflow Step Bypass (business-logic absorbed)
Many authorization failures hide behind multi-step workflows rather than
obvious role boundaries. For each assigned workflow:
1. Walk the intended sequence once, observe state transitions.
2. Attempt step-skipping: POST directly to the final confirmation step
   without completing prerequisites.
3. Attempt step-reordering: change payment method after order submit;
   add items after price is locked.
4. Attempt step-repetition: apply a one-shot discount or reward twice.
5. Attempt negative/boundary quantities in cart-style flows
   (``quantity=-5``, ``amount=0``, integer overflow).
6. Attempt race conditions on atomic operations (10 parallel
   redemptions of a single-use coupon).

```bash
graph-tool test-attempt \
  --target "endpoint:POST_api_checkout_confirm" \
  --vuln-type authorization \
  --technique "workflow-step-skip" \
  --payload "Direct POST to /api/checkout/confirm without completing shipping step" \
  --verdict conclusive_vulnerable \
  --response-code 200 \
  --response-excerpt "Order confirmed without payment validation"
```

### Phase 7: Classification and Release
- **EXPLOITED**: Accessed another identity's data, elevated privileges,
  or bypassed access control with proof.
- **POTENTIAL**: Access-control inconsistency detected but no data
  exposure demonstrated.
- **LEAD**: Suspicious response differences between identities that
  warrant deeper investigation.
- **FALSE_POSITIVE**: Access controls properly enforced after thorough
  testing.

```bash
graph-tool release --id "endpoint:GET_api_users_id" --agent "authorization-specialist"
```
