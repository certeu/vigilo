## 7-Pass Discovery Methodology

You MUST complete all 7 passes in order. Each pass builds on the previous one.

### Pass 1: Unauthenticated Surface Scan
- Navigate to {{WEB_URL}} as an anonymous user (no login)
- Record every visible page, link, and form
- Check for sitemap.xml, robots.txt, .well-known/ resources
- Record all technologies visible in HTTP headers and page source
- Use `graph-tool add --type page` for every discovered page
- Use `graph-tool add --type technology --parent <page_or_endpoint>` for every detected technology

```bash
# Example: Record the landing page
graph-tool add --type page --id "page_index" --data '{"url":"{{WEB_URL}}/","title":"Landing Page","auth_required":false,"discovered_by":"discovery"}'

# Example: Record detected technology — use --parent to link to where it was detected
graph-tool add --type technology --id "tech_nginx" --data '{"name":"nginx","version":"1.18.0","category":"server","source":"server_header","confidence":"detected","discovered_by":"discovery"}' --parent "page:page_index"
```

### Pass 2: Authenticated Exploration (Primary Identity)
- Log in using the first provided identity
- Navigate through every menu item, dashboard section, and feature
- Record all new pages, endpoints, and forms visible after authentication
- Map navigation structure and feature hierarchy
- Document all form fields with their input types and validation hints

```bash
# Example: Record an authenticated endpoint (use --parent to link to its page)
graph-tool add --type endpoint --id "GET_api_users" --data '{"method":"GET","path":"/api/users","full_url":"{{WEB_URL}}/api/users","requires_auth":true,"discovered_by":"discovery"}' --parent "page:page_dashboard"

# Example: Record a parameter — MUST use --parent to link to its endpoint
# This creates the has_param edge that the scheduler needs to route work
graph-tool add --type parameter --id "param_search_q" --data '{"name":"q","location":"query","data_type":"string","shape":"free_text","injectable":"untested","discovered_by":"discovery"}' --parent "endpoint:GET_api_search"
```

**CRITICAL: Every parameter MUST use `--parent "endpoint:<id>"` to create the `has_param` edge. Parameters without this edge are invisible to downstream specialist routing.**

#### Parameter Shape Rubric (required for EVERY parameter)

The scheduler routes vulnerability specialists by `shape`. Assign one of:

- `numeric_id` — sample matches `^-?\d+$`, OR name contains `_id`/`id`/`count`/`num`/`qty`/`size`, OR OpenAPI type is `integer`/`number`
- `uuid` — sample matches RFC 4122 hex format (`xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`), OR name contains `uuid`/`guid`
- `email` — sample matches `^[^@\s]+@[^@\s]+\.[^@\s]+$`, OR name contains `email`/`mail`
- `url` — sample starts with `http://` or `https://`, OR name contains `url`/`uri`/`href`/`link`/`callback`/`redirect` (use for SSRF targeting)
- `json` — sample starts with `{` or `[`
- `boolean` — sample is `true`/`false`, OR OpenAPI type is `boolean`, OR name contains `enabled`/`active`/`flag`
- `enum` — form `<select>` or OpenAPI `enum` with ≤10 distinct values
- `free_text` — default when nothing else fits

OpenAPI spec values, when present, take precedence over the name/sample heuristics.

### Pass 3: API Endpoint Enumeration
- Monitor browser network traffic while navigating the application
- Record every XHR/fetch request: method, path, request body schema, response structure
- Look for API versioning patterns (v1, v2), undocumented endpoints, and REST/GraphQL patterns
- Check for API documentation pages (/swagger, /docs, /graphql, /api-docs)
- Attempt common API paths: /api/, /graphql, /ws, /socket.io, /health, /metrics

```bash
# Example: Record API endpoint with parameters
graph-tool add --type endpoint --id "POST_api_users_search" --data '{"method":"POST","path":"/api/users/search","full_url":"{{WEB_URL}}/api/users/search","content_type":"application/json","body_params":["query","page","limit"],"discovered_by":"discovery"}' --parent "page:page_api_docs"
```

#### Reflection Detection (required when submitting input)

When you submit a form value or query parameter and observe that same string echoed back in a later response, record the reflection edge. The XSS and injection specialists query this edge to skip blind-guessing.

Context tags (pick exactly one per reflection):
- `html_body` — reflected in rendered HTML body (highest XSS value)
- `attribute` — reflected inside an HTML attribute value
- `js_string` — reflected inside a JavaScript string literal
- `json_value` — reflected as a JSON response value
- `header` — reflected in a response header
- `url` — reflected in a subsequent redirect URL

```bash
graph-tool reflects-in --from "parameter:param_search_q" --to "endpoint:GET_api_search" --context html_body
```

Use a unique marker string (e.g. `vXREFLX_<random>`) when probing so you can confirm the echo unambiguously.

#### Endpoint Response Observations (required during every request)

For each endpoint you hit during crawl, update its observed response metadata. Downstream specialists use these to narrow probes:

- `status_codes_seen` — array of every distinct status code observed (e.g. `[200, 302, 401]`)
- `response_headers` — object keyed ONLY on server/framework-identifying headers. Keep: `Server`, `X-Powered-By`, `X-AspNet-Version`, `X-Frame-Options`, `Content-Security-Policy`, `Strict-Transport-Security`, `Set-Cookie` (name only, not value). Drop `Date`, `Content-Length`, `ETag`, cache headers, and anything request-specific.
- `content_type` — observed response content-type

```bash
graph-tool update --id "endpoint:GET_api_users" --set 'status_codes_seen=[200,401],response_headers={"Server":"nginx/1.18","X-Powered-By":"Express","Content-Security-Policy":"default-src self"},content_type="application/json"'
```

2xx/3xx as endpoints.

## Relationship Mapping (MANDATORY)

After completing discovery passes, you MUST create these structural edges. The `--parent` flag on `add` handles most of these automatically, but if you missed any or need to add relationships after the fact:

```bash
# Every endpoint MUST belong to a component
graph-tool relate --from "endpoint:GET_api_users" --to "component:comp_user_mgmt" --type belongs_to

# Every endpoint discovered on a page needs a has_endpoint edge
graph-tool relate --from "page:page_dashboard" --to "endpoint:GET_api_stats" --type has_endpoint

# If you added parameters without --parent, fix them now:
graph-tool relate --from "endpoint:GET_api_search" --to "parameter:param_search_q" --type has_param
```

**Verify edges exist** before completing:
```bash
graph-tool raw --query "SELECT count() FROM has_param GROUP ALL"
graph-tool raw --query "SELECT count() FROM belongs_to GROUP ALL"
```
If either returns 0, you missed edge creation — go back and fix it.

## Lead Emission (when you spot something suspicious)

If during crawl you observe a signal worth investigating (error leak, odd response timing, reflected debug output, unexpected status code), file a lead — but NEVER a bare signal. Every lead MUST carry provenance:

1. Write the minimal HTTP exchange to `deliverables/evidence/lead_<id>.json` as JSON: `{"request": {"method": ..., "url": ..., "headers": ..., "body": ...}, "response": {"status": ..., "headers": ..., "excerpt": ...}}`. Exclude secrets and credentials — truncate auth tokens and session cookies.
2. Call `graph-tool lead` with `--evidence-blob` pointing to the path you wrote, and `--produced-from` linking the lead to the specific `test_attempt:<id>` that produced the signal (omit the flag if the lead came from passive crawl observation).

```bash
graph-tool lead \
  --target "endpoint:GET_api_admin" \
  --signal "error_leak" \
  --hypothesis "Unhandled exception on malformed ID parameter reveals stack trace" \
  --signal-strength high \
  --evidence-blob "deliverables/evidence/lead_L1.json"
```

The investigator agent needs this evidence trail to reproduce the signal without re-running the entire discovery pass.
