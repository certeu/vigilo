## WebSocket Security Testing Methodology (Grey-Box)

### Phase 1: Connection Analysis
1. Identify WebSocket endpoints from the graph (ws://, wss://, /socket.io/, /ws)
2. Analyze the WebSocket handshake:
   - What authentication tokens are sent during upgrade?
   - Is Origin header validated?
   - What subprotocols are negotiated?
3. Capture and analyze message formats (JSON, binary, custom protocol)

```bash
graph-tool claim --id "endpoint:WS_socket" --agent "websocket-specialist" --ttl 600

graph-tool test-attempt \
  --target "endpoint:WS_socket" \
  --vuln-type websocket_analysis \
  --technique "handshake-analysis" \
  --payload "WebSocket upgrade request analysis" \
  --result inconclusive \
  --response-code 101 \
  --response-excerpt "Upgrade successful, JWT sent in first message, JSON protocol"
```

### Phase 2: Authentication Testing
Test if WebSocket connections enforce authentication:

1. **Unauthenticated connection**: Attempt to connect without any auth tokens
2. **Expired token**: Use an expired session/JWT for the connection
3. **No handshake auth**: Connect and send messages without initial auth message
4. **Token replay**: Reuse a token from a logged-out session

```bash
graph-tool test-attempt \
  --target "endpoint:WS_socket" \
  --vuln-type websocket_auth_bypass \
  --technique "unauthenticated-connection" \
  --payload "WebSocket connect without session cookie or JWT" \
  --result success \
  --response-code 101 \
  --response-excerpt "Connection accepted — server sends data without authentication"
```

### Phase 3: Cross-Site WebSocket Hijacking (CSWSH)
Test if Origin header is validated during the handshake:
1. Send WebSocket upgrade with `Origin: https://evil-site.com`
2. If connection accepted, CSWSH is possible (attacker page can connect to victim's WebSocket)
3. Verify by connecting with a completely different origin and receiving data

```bash
graph-tool test-attempt \
  --target "endpoint:WS_socket" \
  --vuln-type cswsh \
  --technique "origin-bypass" \
  --payload "WebSocket upgrade with Origin: https://attacker.com" \
  --result success \
  --response-code 101 \
  --response-excerpt "Connection accepted with foreign origin — CSWSH possible"
```

### Phase 4: Authorization Testing
Test if per-message authorization is enforced:
1. **Channel subscription**: Subscribe to channels belonging to other users
2. **Admin messages**: Send admin-level commands from a regular user connection
3. **Room access**: Join rooms/channels you should not have access to
4. **Message targeting**: Send messages to other users' private channels

```bash
graph-tool test-attempt \
  --target "endpoint:WS_socket" \
  --vuln-type websocket_authz \
  --technique "unauthorized-channel-subscribe" \
  --payload '{"action":"subscribe","channel":"admin-notifications"}' \
  --result success \
  --response-code 200 \
  --response-excerpt "Subscribed to admin channel — receiving admin notifications as regular user"
```

### Phase 5: Message Injection and Manipulation
Test if WebSocket messages are validated:
1. **SQL injection through messages**: Send SQL payloads in message fields
2. **XSS via messages**: Inject HTML/JS in chat messages displayed to other users
3. **Command injection**: If messages trigger server-side processing
4. **Message format abuse**: Send malformed JSON, oversized messages, or unexpected types

```bash
graph-tool test-attempt \
  --target "endpoint:WS_socket" \
  --vuln-type sqli \
  --technique "websocket-message-injection" \
  --payload '{"action":"search","query":"test'"'"' OR 1=1--"}' \
  --result fail \
  --response-code 200 \
  --response-excerpt "Search results unchanged — input sanitized"
```

### Phase 6: Data Leakage
Monitor WebSocket traffic for unintended data exposure:
1. Listen for messages that include other users' data
2. Check if server broadcasts contain sensitive fields (tokens, passwords, internal IDs)
3. Test if disconnected users' messages are replayed to new connections
4. Check if error messages reveal internal details

### Phase 7: Denial of Service
Test connection and message limits:
1. Attempt to open many concurrent connections
2. Send rapid-fire messages (rate limiting test)
3. Send very large messages (size limit test)
4. Send messages in unexpected format to trigger errors

### Phase 8: Classification
- **EXPLOITED**: Unauthorized data access, CSWSH confirmed, or injection via WebSocket
- **POTENTIAL**: Missing origin check but no data exposure demonstrated
- **LEAD**: Suspicious message handling or incomplete auth enforcement
- **FALSE_POSITIVE**: WebSocket properly secured after thorough testing

```bash
graph-tool finding \
  --target "endpoint:WS_socket" \
  --vuln-type cswsh \
  --severity high \
  --cwe CWE-346 \
  --title "Cross-Site WebSocket Hijacking — no Origin validation" \
  --poc-payload "WebSocket upgrade accepted from any Origin header" \
  --impact "Attacker-controlled page can hijack authenticated WebSocket and receive real-time data" \
  --grants '["data_theft","session_hijack"]' \
  --requires '["victim_visits_attacker_page"]' \
  --evidence-file "deliverables/screenshots/ws-cswsh.png" \
  --derived-from "test_attempt:ta_XXXX"

graph-tool release --id "endpoint:WS_socket" --agent "websocket-specialist"
```
