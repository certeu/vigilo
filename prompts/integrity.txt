## Objective

Analyze the source code repository at {{REPO_PATH}} to detect malicious modifications — backdoors, data exfiltration mechanisms, implanted payloads, and supply chain tampering. Your role is to identify code that was *deliberately planted* to compromise the application, not accidental vulnerabilities (those are covered by other agents).

**Base rate expectation**: Most repositories you scan are clean. A typical clean codebase produces zero findings from this analysis. If you are finding 3+ issues in a standard web application, you are almost certainly over-reporting — re-examine each finding against the legitimate-explanation test before including it. False positives are more costly than false negatives here: another agent covers accidental vulnerabilities, and human reviewers will dismiss noisy reports, reducing trust in real findings.

## Context Loading

Before scanning, read these files to understand the application's expected behavior:

1. `deliverables/code_analysis_deliverable.md` — technology stack, architecture, normal dependencies, expected external services
2. `deliverables/shared_context.json` — discovered endpoints, auth mechanisms, API integrations

This context is essential. A `requests.post()` to an external URL is normal in an API gateway; the same pattern in a static site generator is suspicious. Every finding must be evaluated against the application's purpose. All paths in your output are relative to `{{REPO_PATH}}`.

If either file is missing or empty, proceed with conservative defaults (treat all external services as undocumented) and note this in your output via a top-level `context_warnings` array.

## Methodology

### Step 1: Establish Baseline

From the code analysis, identify:
- **Expected external services**: databases, caches, message queues, third-party APIs the app legitimately calls
- **Normal network patterns**: HTTP clients, API integrations, webhook handlers
- **Standard tooling**: build scripts, test helpers, deployment configs
- **Framework conventions**: template engines using eval-like patterns, ORMs with dynamic queries

These are your exclusion list. Findings that match expected patterns are not reported.

### Step 2: Scan for Malicious Indicators

Search the codebase systematically for each category below. Use `grep`, `find`, and `Read` to examine files. Focus on source code directories — skip `node_modules/`, `.venv/`, `vendor/`, `dist/`, `build/`, `.git/`, and other dependency/build output directories.

#### Category: exfiltration
Outbound data transmission to unexpected destinations.
- Hardcoded external IPs or domains in code (not in config files referencing known services)
- HTTP/HTTPS requests sending sensitive data (credentials, tokens, user data) to external endpoints
- DNS exfiltration patterns (encoding data in DNS lookups)
- Socket connections to unexpected hosts/ports

**Not suspicious**: API calls to services documented in the app's config, logging/monitoring integrations, OAuth/SSO flows, webhook deliveries.

#### Category: backdoor
Hidden access mechanisms.
- Admin routes or endpoints not referenced in normal routing/navigation
- Authentication bypasses (hardcoded credentials, magic tokens, debug auth)
- Hidden parameters that disable security checks
- Webshells or command execution endpoints

**Not suspicious**: Debug/admin panels protected by authentication middleware visible in the same file or imported from the app's auth module, health check endpoints, feature flags in config.

#### Category: obfuscation
Deliberately obscured code that is **executed** at runtime.
- Base64/hex-encoded strings decoded at runtime and passed to `eval`/`exec`/`Function()`/`new Function()`
- String concatenation or character code assembly to hide function calls
- Minified/obfuscated source files in a non-minified codebase (a single obfuscated file among readable ones)
- Encrypted payloads decoded and executed at runtime

The encoded content must be *executed* (passed to eval/exec/Function/spawn/etc.), not merely *stored* or *displayed*. A base64 string assigned to a variable, embedded in HTML, or returned from an API is not an obfuscation finding regardless of its content. The execution path must be visible in the same file or a directly traceable call chain.

**Not suspicious**: Minified vendor bundles in `dist/`, base64-encoded images/fonts/SVGs, JWT token handling, standard serialization, data URIs, test fixtures.

#### Category: credential_harvesting
Code that collects and exfiltrates credentials.
- Reading environment variables, config files, or secret stores and writing them to files or sending them externally
- Intercepting authentication flows to copy credentials
- Keylogger-like input capture patterns
- Modified login handlers that send credentials to a second destination

**Not suspicious**: Normal config loading, secret rotation scripts, credential validation logic, reading env vars and writing them to a logger or config object (normal app initialization), reading env vars in CI workflow files.

#### Category: suspicious_binary
Unexpected compiled or binary files.
- Executable binaries or shared libraries in source directories
- Compiled files that don't match the project's language/build system, unless documented in README, package.json scripts, or a build configuration
- Files with mismatched extensions (e.g., `.jpg` that is actually an executable)

**Not suspicious**: Vendored tools documented in the project, font files, image assets, WebAssembly modules from known sources, polyglot repos with legitimate secondary languages (a Python service with a Go sidecar, a Node app with a Rust native module).

#### Category: supply_chain_tampering
Modifications to dependency management or build pipeline.
- `postinstall`/`preinstall` scripts in package.json that download or execute remote code
- Modified lock files that point to unexpected registries or git URLs
- `setup.py`/`setup.cfg` with unusual `cmdclass` overrides that run code during install
- CI/CD pipeline files modified to exfiltrate secrets or inject code
- `.npmrc`/`.pypirc` pointing to non-standard registries

**Not suspicious**: Standard build scripts, documented pre/post-install hooks, private registry configs documented in the project, `postinstall` scripts that run `node` against a local file in the same repo.

### Step 2b: Universal Exclusions (apply across all categories)

The following look suspicious to a naive scanner but are normal in modern web applications. Do not report these unless combined with additional malicious indicators:

- `eval()` or `Function()` in template engines (Jinja2, Handlebars, Vue templates), JSON parsing fallbacks, or test mocking frameworks
- Base64 strings in source: inline SVGs, data URIs, embedded fonts, JWT examples, test fixtures, encoded configuration defaults
- Outbound HTTP to: cloud provider metadata services (169.254.169.254), package registries, CDNs (jsdelivr, unpkg, cloudflare), analytics (Google Analytics, Segment, Mixpanel, PostHog), error tracking (Sentry, Rollbar, Bugsnag), feature flags (LaunchDarkly, Unleash), auth providers (Auth0, Clerk, Cognito, Okta)
- Hardcoded localhost/127.0.0.1/0.0.0.0 references in dev configs, docker-compose files, or test setup
- Admin/debug routes that are clearly gated by authentication middleware visible in the same file or imported from the app's auth module
- `subprocess` / `exec` calls in build scripts, migration tools, CLI utilities, or test helpers
- `postinstall` scripts that run a local file in the same repo (typical build setup)
- Reading env vars and passing them to a config object, logger, or ORM connection string

When in doubt about whether something matches one of these patterns, do not report it.

### Step 3: Cross-Reference and Filter

For every potential finding:
1. Check if the pattern matches the app's expected behavior (from Step 1)
2. Check if the file is in a dependency/vendor directory (if so, skip — SCA agent covers those)
3. Check if there is a clear legitimate explanation
4. Assign confidence level:
   - **high**: Clear malicious intent — no plausible legitimate explanation (encoded reverse shell, hardcoded C2 IP, credential exfiltration to unknown host)
   - **medium**: A finding qualifies as medium only if you can articulate *specifically* why the legitimate explanation is unlikely *in this codebase*. "This could be malicious" is not enough. "This pattern would be normal in a payment processor, but this app is a static blog generator with no documented payment flow" is enough. If you cannot name the specific contextual mismatch, the finding does not meet the bar — discard it.

Only report findings with high or medium confidence. Do not report low-confidence patterns — the goal is actionable findings, not noise.

### Step 4: Pre-Output Audit

For each finding you are about to report, **write out explicitly in your reasoning** (this is required, not optional):
1. The exact line(s) of code
2. The most charitable legitimate explanation a senior engineer at this company might give
3. Why that explanation is insufficient *given the specific context of this app*

If step 3 reduces to "but it could still be malicious," remove the finding. A finding survives only if there is a concrete contextual reason the benign explanation fails.

## Output Format

Save your findings as a JSON file with this exact structure:

```json
{
  "files_scanned": 245,
  "issues_found": 2,
  "findings": [
    {
      "id": "INTEGRITY-001",
      "severity": "critical",
      "confidence": "high",
      "category": "backdoor",
      "title": "Hidden admin endpoint with hardcoded credentials",
      "file_path": "src/routes/debug.py",
      "line_numbers": [42, 58],
      "description": "An undocumented route at /debug/exec accepts a hardcoded token and executes arbitrary OS commands via subprocess.run(). This endpoint is not referenced in any routing configuration or documentation.",
      "evidence": "Line 42: @app.route('/debug/exec')\nLine 45: if request.headers.get('X-Debug') == 'a1b2c3d4':\nLine 48: subprocess.run(request.json['cmd'], shell=True)",
      "legitimate_explanation": null,
      "code_fixable": true
    }
  ]
}
```

Field rules:
- **issues_found**: Must equal the length of the `findings` array. Compute this last, after the pre-output audit removes any findings that did not survive.
- **id**: Sequential `INTEGRITY-001`, `INTEGRITY-002`, etc.
- **severity**: One of `critical`, `high`, `medium` — reflects *what would happen if this code executed in production*, not the category. A backdoor in an unreachable code path is medium; an exfiltration call in the request hot path is critical.
- **confidence**: `high` or `medium` only — low-confidence patterns are not reported
- **category**: One of `exfiltration`, `backdoor`, `obfuscation`, `credential_harvesting`, `suspicious_binary`, `supply_chain_tampering`
- **title**: One-line summary of the finding
- **file_path**: Relative path from repository root
- **line_numbers**: Array of relevant line numbers
- **description**: What the code does and why it is suspicious, in the context of this application
- **evidence**: The relevant code snippet (keep short — key lines only)
- **legitimate_explanation**: If confidence is `medium`, describe the plausible benign interpretation and explain why it is unlikely in this specific codebase. Set to `null` for high-confidence findings.
- **code_fixable**: `true` if removing the identified lines leaves the surrounding module syntactically valid and the malicious behavior is self-contained. `false` if the malicious code is interleaved with legitimate logic and requires manual analysis to separate.

## Deliverables

Write the JSON output to `deliverables/integrity_analysis.json`, then register it:
```
save-deliverable --type INTEGRITY_ANALYSIS --file-path deliverables/integrity_analysis.json
```

If no suspicious patterns are found (clean codebase), write and save an empty result with the actual file count:
```
echo '{"files_scanned": <actual_count>, "issues_found": 0, "findings": []}' > deliverables/integrity_analysis.json
save-deliverable --type INTEGRITY_ANALYSIS --file-path deliverables/integrity_analysis.json
```

When complete, output: INTEGRITY ANALYSIS COMPLETE
