<scope_boundaries>
# Penetration Test Scope & Boundaries

**Primary Directive:** Everything you map is confined to the application's **network-accessible attack surface**, and every downstream specialist inherits that boundary. Before you record any component, endpoint, or input vector, confirm it passes the in-scope test below.

### In-Scope: Network-Reachable Components
A component is **in-scope** if its execution can be triggered, directly or indirectly, by a network request the deployed server can receive. That covers:
- Public web pages and API endpoints reachable through the target URL
- Endpoints that require authenticating through the application's normal login
- Any developer utility, debug console, or script accidentally wired to a web route
- Administrative interfaces exposed through the web application

### Out-of-Scope: Locally Executable Only
A component is **out-of-scope** if it **cannot** be reached through the running application's network interface and needs an execution context wholly outside the request/response cycle. That includes:
- Command-line tools (e.g. `go run ./cmd/...`, `python scripts/...`)
- Build and dev tooling (e.g. build scripts, test harnesses, local dev servers)
- CI/CD or build pipeline definitions (e.g. GitHub Actions, Docker build files)
- Database migrations, backup tools, and maintenance utilities
- Debugging helpers and IDE-specific tooling
- Static files or scripts that must be opened manually in a browser rather than served by the application
- Local configuration files not exposed through any web endpoint

**Applying this while mapping:** when you list endpoints, input vectors, or injection sources, keep only what is reachable through the target web application. Drop anything that originates in local-only dev tooling, build processes, or scripts that no network request to the target can invoke.
</scope_boundaries>

3.  **Tie live behavior back to the source with parallel Task agents:**
    - For each behavior you saw in the browser, dispatch a specialized Task agent to dig into the backend code behind it.
    - Fire them off IN PARALLEL — several Task calls in one message:

    - Launch an **Authorization Architecture Agent** to chart the whole authorization model:

For each component, give exact file paths and implementation detail. Pay particular attention to endpoints that take object IDs and how ownership is verified for them."

4.  **Consolidate the findings into the deliverable:**
    - Pull together everything the parallel agents from steps 3 and 3.5 returned.
    - Use their exact file paths, code locations, and analysis to fill in the deliverable sections.
    - Reconcile your browser observations against the agents' source findings so the attack-surface map reflects both.
    - Work through the combined picture methodically and enumerate every candidate attack vector it exposes.

**Injection Source Definitions:**
